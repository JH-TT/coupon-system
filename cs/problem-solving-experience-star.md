# 문제 해결 사례 (면접 STAR 포맷)

## STAR 1) 대규모 트래픽에서 쿠폰 발급 성공률 급락 해결

### S (Situation)
- 선착순 쿠폰 API에서 요청량이 올라가자 성공률이 급격히 낮아지고 응답 지연이 커졌습니다.
- 기존 구조는 요청 처리 경로 안에서 수량 확인과 DB 저장을 모두 수행하는 동기 방식이었습니다.

### T (Task)
- 고부하에서도 정합성을 유지하면서 API 응답 성능을 안정화해야 했습니다.
- 단순 튜닝이 아니라 병목의 근본 원인을 확인하고 구조적 개선안을 제시하는 것이 목표였습니다.

### A (Action)
- 부하 테스트(k6)로 실패율, 응답시간, dropped 요청을 계측하며 병목 지점을 분해했습니다.
- 요청 경로를 비동기 이벤트 기반으로 전환해 DB 작업을 응답 경로에서 분리했습니다.
- 수량 기준을 Redis로 단일화하고, DB에는 유니크 제약으로 최종 중복 방지를 강제했습니다.

### R (Result)
- 동일한 고부하 조건에서 동기 처리 대비 비동기 분리 후 지표를 개선했습니다.
  - 2,000 req/s 기준: 평균 응답시간 `70ms -> 6~17ms(워밍업 후)`
  - 성공률: `21.6% -> 100%`
  - dropped iterations: `662 -> 0`
- 데이터 정합성도 유지했습니다. 수량 제한 테스트에서 Redis 카운트와 DB 발급 건수가 동일하게 맞는 것을 확인했습니다.
- 병목이 DB 커넥션 풀에서 애플리케이션 수용량(스레드/큐)으로 이동함을 확인해, 다음 확장 전략(수평 확장)의 근거를 확보했습니다.

## STAR 2) 비동기 구조에서 정합성 보장을 위한 보상 트랜잭션 설계

### S (Situation)
- 비동기 구조에서 "수량은 증가했는데 이벤트 발행/소비가 실패"하면 수량과 실제 발급 결과가 어긋날 수 있었습니다.

### T (Task)
- 실패 구간별로 안전하게 원복되면서도, 재시도 환경에서 중복 보상(과보상)이 발생하지 않도록 설계해야 했습니다.

### A (Action)
- 실패를 발행 단계와 소비 단계로 분리했습니다.
  - 발행 실패: 즉시 원복
  - 소비 실패: 1회 보상 마커로 중복 보상 차단
- 중복키 오류는 실제 실패가 아니라 "이미 처리된 이벤트"로 간주하는 idempotent 분기를 추가했습니다.

### R (Result)
- 재시도 환경에서 발생하던 중복 처리 오류(`uk_coupon_user`)를 idempotent 분기로 흡수해, 동일 이벤트 재처리 루프를 줄였습니다.
- 발행 실패/소비 실패를 분리해 보상한 뒤, 수량 제한 테스트에서 Redis/DB 발급 건수 일치(정확히 1,000건)를 유지했습니다.
- 운영 시나리오(장애/재기동/재시도)에서도 과보상 방지(1회 보상 마커)로 일관성을 확보했습니다.

## STAR 3) 고부하에서 거절 응답이 더 느려지는 역전 현상 해결

### S (Situation)
- 수량 초과 요청은 정상 거절(409)이어야 하는데, 고부하에서 오히려 응답 지연이 커지는 현상이 발생했습니다.

### T (Task)
- 실패 케이스에서도 처리 경로를 가볍게 만들어 전체 시스템 지연을 낮춰야 했습니다.

### A (Action)
- 기본 에러 처리 경로를 분석하고, 공통 예외 처리로 즉시 응답하도록 단순화했습니다.
- 예외를 던지는 방식 vs 반환 방식을 반복 실험으로 비교해 편차를 제거했습니다.

### R (Result)
- 공통 예외 처리 도입 전/후를 동일 조건으로 비교해 병목을 수치로 확인했습니다.
  - dropped: `10,308 -> 665`
  - 평균 응답시간: `736.64ms -> 109.46ms`
  - 최대 응답시간: `3.54s -> 995.84ms`
- 이후 5회 반복 실험으로 워밍업 효과를 분리해 해석했습니다.
  - 워밍업 후(2~4회차): 평균 `6~38ms` 구간 안정
  - 재시작 직후(1회차/5회차): 평균 `90~127ms`로 저하

## STAR 4) Kafka vs @Async 기술 선택 근거 수립

### S (Situation)
- 비동기 처리 방식으로 메시지 브로커를 유지할지, 애플리케이션 내부 비동기(@Async)로 단순화할지 의사결정이 필요했습니다.

### T (Task)
- 기능 동작 여부를 넘어, 정합성/지연/처리량/운영 안정성까지 포함한 선택 기준을 만들어야 했습니다.

### A (Action)
- 동일 트래픽/동일 수량 제한 조건으로 Kafka와 @Async를 반복 비교했습니다.
- 평균값뿐 아니라 성공 요청 지연, 실패 구성, 처리량 상한을 함께 분석했습니다.

### R (Result)
- 동일 조건(쿠폰 1,000개, 약 2,700~3,100 RPS)에서 두 방식 모두 정합성은 동일하게 충족했습니다(정확히 1,000건 발급).
- 전체 응답성능은 유사했습니다.
  - Kafka: avg `~705~759ms`, p95 `~900ms~1.1s`
  - @Async: avg `~688~700ms`, p95 `~900ms`
- 성공 요청 latency는 Kafka가 우수했습니다.
  - Kafka: `~87~107ms`
  - @Async: `~175~321ms`
- 처리량은 둘 다 약 `90건/sec`로 유사해, 최종 상한은 비동기 도구보다 DB/락/트랜잭션 구조에 의해 결정된다는 결론을 얻었습니다.

---

## 면접에서 강조할 포인트
- 문제를 "증상"이 아니라 "경로/구조" 단위로 분해한 점
- 정합성을 로직/DB 제약/재시도 정책으로 통합 설계한 점
- 반복 실험으로 편차를 제거하고 수치 기반으로 결론을 낸 점
- 성능뿐 아니라 장애 복구/운영 안정성까지 고려해 기술을 선택한 점
