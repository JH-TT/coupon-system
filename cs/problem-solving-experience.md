# 대규모 트래픽 쿠폰 발급 시스템 문제 해결 사례

아래 내용은 특정 프로젝트 내부 용어 없이, 제3자가 읽어도 맥락을 이해할 수 있도록 정리한 개발 개선 사례입니다.

## 1) 요청은 많은데 성공률이 급락한 문제 해결

### 문제 상황
- 선착순 쿠폰 발급 API에서 트래픽이 증가할수록 실패율이 급격히 상승했습니다.
- 초기 구조는 요청 처리 경로 안에서 Redis 수량 체크와 DB 저장을 모두 수행하는 동기 방식이었습니다.
- 이 구조에서 DB 커넥션 풀이 빠르게 포화되어 응답 지연과 실패가 동시에 증가했습니다.

### 원인 분석
- 수량 제어를 Redis로 하더라도, API 응답 경로에 DB INSERT가 남아 있으면 결국 DB가 병목이 됩니다.
- 락을 강하게 걸면 정합성은 좋아지지만 직렬화 때문에 처리량이 낮아지고, 락을 줄이면 동시성 문제가 재발했습니다.

### 개선 내용
- 아키텍처를 비동기 이벤트 기반으로 전환했습니다.
- 요청 경로는 `수량 확인 -> 이벤트 발행 -> 즉시 응답`으로 단순화하고,
- 실제 발급 저장은 별도 소비자(consumer)가 백그라운드에서 처리하도록 분리했습니다.

### 결과
- 응답 경로에서 DB 작업이 제거되면서 체감 지연과 실패율이 크게 개선되었습니다.
- 동일 부하 조건에서 평균 응답시간이 안정적으로 낮아졌고, 성공률이 유의미하게 향상되었습니다.
- 병목 지점이 DB에서 애플리케이션 수용량(스레드/큐)으로 이동한 것을 확인했습니다.

---

## 2) 중복 발급/정합성 깨짐 문제를 구조적으로 방지

### 문제 상황
- 고부하에서 동일 사용자 중복 발급, 카운트 불일치 등 데이터 정합성 문제가 발생했습니다.

### 원인 분석
- 수량을 Redis와 DB에서 동시에 관리하면 기준이 분산되어 불일치 가능성이 커집니다.
- 애플리케이션에서 `조회 후 저장(find -> insert)` 패턴은 동시성 환경에서 경쟁 조건에 취약합니다.

### 개선 내용
- 수량은 Redis를 단일 기준으로 통일했습니다.
- 최종 중복 방지는 DB 유니크 제약(쿠폰 ID + 사용자 ID 조합)으로 강제했습니다.
- 이벤트 재처리 환경을 고려해, 중복키 오류를 "이미 처리된 요청"으로 분기하는 idempotent 처리 로직을 적용했습니다.

### 결과
- 중복 발급 방지와 수량 정합성을 동시에 확보했습니다.
- 재시도 환경에서도 같은 이벤트가 여러 번 반영되는 문제를 줄였습니다.

---

## 3) 비동기 구조 실패 시 보상 트랜잭션 설계

### 문제 상황
- 수량 카운트 증가 후, 이벤트 발행 또는 소비 단계에서 실패하면 수량과 실제 발급 데이터가 어긋날 수 있었습니다.

### 개선 내용
1. 발행 단계 실패 보상
   - 이벤트 발행 실패를 감지하면 즉시 수량을 원복하도록 처리했습니다.
2. 소비 단계 실패 보상
   - 소비 실패 시 수량 원복을 수행하되, 같은 이벤트에 대해 중복 보상이 일어나지 않도록 "1회 보상" 마커를 적용했습니다.
3. 실패 유형 분리
   - 중복 이벤트는 보상 대상이 아닌 완료 처리로 분기하고,
   - 실제 비정상 실패만 보상/에러 처리 대상으로 제한했습니다.

### 결과
- "증가만 되고 실제 발급은 실패"하는 불일치 케이스를 줄였습니다.
- 재시도 상황에서도 과보상(중복 원복) 위험을 방지했습니다.

---

## 4) 에러 처리 경로 최적화로 지연 역전 현상 해소

### 문제 상황
- 수량 초과 요청은 정상 거절(예: 409)이어야 하는데, 고부하에서 거절 응답이 성공 응답보다 더 느려지는 현상이 발생했습니다.

### 원인 분석
- 프레임워크 기본 에러 처리 경로(내부 포워딩 포함)가 포화 상황에서 추가 지연을 유발했습니다.

### 개선 내용
- 공통 예외 처리 레이어를 통해 거절 응답을 즉시 반환하도록 단순화했습니다.
- 예외를 던지는 방식과 결과를 반환하는 방식 두 가지를 모두 동일 부하로 비교 검증했습니다.

### 결과
- tail latency와 dropped 요청이 크게 줄었고, 전체 처리 안정성이 개선되었습니다.
- 단발 실험이 아닌 반복 실험으로 검증해 결론 신뢰도를 높였습니다.

---

## 5) Kafka vs @Async 비교를 통한 기술 선택 근거 확보

### 문제 상황
- 비동기 처리를 메시지 브로커 기반으로 유지할지, 애플리케이션 내부 비동기(@Async)로 단순화할지 판단이 필요했습니다.

### 실험 방법
- 동일한 발급 수량 제한, 동일한 요청률 조건에서 두 방식을 반복 측정했습니다.
- 정합성(정확히 제한 수량만 발급), 응답시간, 처리량, 실패율 구성을 함께 비교했습니다.

### 결과 및 해석
- 두 방식 모두 정합성은 동일하게 만족했습니다.
- 전체 응답시간은 유사했지만, 실제 성공 요청 처리 지연은 메시지 브로커 기반 방식이 더 안정적으로 낮았습니다.
- 최종 처리량 상한은 비동기 도구 선택보다 DB/트랜잭션 구조의 영향을 더 크게 받았습니다.

### 비즈니스 관점 의미
- 단순 평균 응답시간만이 아니라, 장애 복구/내구성/재처리 전략까지 포함한 기술 선택 근거를 확보했습니다.

---

## 6) 리팩토링 관점에서의 개선 포인트

- 동기 중심 처리 흐름을 비동기 이벤트 흐름으로 단계적으로 분리했습니다.
- 실패 처리 책임을 단계별로 재배치해(발행 실패, 소비 실패, 중복 이벤트) 유지보수성을 높였습니다.
- 운영 로그를 원인 추적 중심으로 재정비해 장애 분석 시간을 단축했습니다.
- 실험 결과를 문서화해 재현 가능한 개선 사이클(측정 -> 원인 분석 -> 개선 -> 재측정)을 구축했습니다.

---

## 7) 핵심 성과 요약

이 사례의 핵심은 기능 구현 자체보다, 트래픽 증가 시 시스템이 왜 무너지는지 수치로 확인하고 구조를 바꿔 해결했다는 점입니다.

- 병목은 코드 한 줄이 아니라 시스템 경로에서 발생한다.
- 정합성은 애플리케이션 로직과 저장소 제약, 재시도 정책을 함께 설계해야 유지된다.
- 성능 결론은 단발 측정이 아니라 반복 실험과 워밍업 분리로 검증해야 신뢰할 수 있다.
